# プロパティ定義書

4つのデータベースの列（プロパティ）定義。
**「インポート後に追加」** と書かれたものは CSV では作れないため、Notion 上で手動作成する。

---

## ① クライアントDB（企業DB）

### CSV に含まれる列

| プロパティ名 | 型 | 備考 |
|---|---|---|
| 会社名 | タイトル | 正式名称で統一する（「株式会社」の位置まで揃える） |
| 業種 | セレクト | 商社 / 情報通信 / 製造 / 金融 / 医療 / 公共 / その他 |
| 所在地 | テキスト | |
| 担当者名 | テキスト | 主担当1名。複数いる場合は本文に書く |
| 担当者部署役職 | テキスト | |
| 担当者メール | メール | |
| 初回取引日 | 日付 | |
| 取引ステータス | セレクト | 取引中 / 休眠 / 見込み / 取引終了 |
| 備考 | テキスト | 商習慣・注意点・キーパーソンの特徴など |

### インポート後に追加

| プロパティ名 | 型 | 設定内容 |
|---|---|---|
| 案件 | リレーション | 案件DB。**「案件DBにも表示する」をON**（双方向にする） |
| 案件数 | ロールアップ | リレーション`案件` → プロパティ`案件名` → 計算`元の値をカウント` |
| 累計受注額 | ロールアップ | リレーション`案件` → プロパティ`受注金額` → 計算`合計` |
| 最新案件日 | ロールアップ | リレーション`案件` → プロパティ`研修実施日` → 計算`最新の日付` |

## ② 案件DB（研修DB）★中心

### CSV に含まれる列

| プロパティ名 | 型 | 備考 |
|---|---|---|
| 案件名 | タイトル | 命名規則 `クライアント名_研修名_実施年月` |
| クライアント | テキスト → **リレーション** | インポート後に型変換（手順は README 参照） |
| ステータス | テキスト → **ステータス** | 下表参照 |
| 研修実施日 | 日付 | カレンダー／タイムラインの基準になる |
| 営業担当 | テキスト → ユーザー（任意） | Notion メンバーが揃ってから変換する |
| 担当講師 | テキスト | 業務委託講師は Notion アカウントを持たない前提でテキストのまま |
| 講師区分 | セレクト | 社員 / 業務委託 / 未定 |
| 研修テーマ | テキスト → **マルチセレクト** | カンマ区切りで複数指定 |
| 受注金額 | 数値 | 表示形式を「円」にする |
| 現状サマリー | テキスト | ★**最重要**。案件を知らない人が最初に読む3〜5行 |
| 次のアクション | テキスト | 「誰が何をするか」を1文で |
| 次のアクション期限 | 日付 | |
| SharePointリンク | URL | 案件のドキュメントセットURL |

### ステータスの選択肢とグループ

| グループ | 選択肢 |
|---|---|
| 未着手（To-do） | 引合 / 提案中 |
| 進行中（In progress） | 受注 / 準備中 / 実施待ち |
| 完了（Complete） | 実施済 / 請求済 / 完了 / 失注 |

> ステータス型はこのグループ分けを持つため、セレクト型ではなくステータス型を使う。
> ボードビューで「未着手・進行中・完了」の3レーンに自動集約され、俯瞰しやすくなる。

### インポート後に追加

| プロパティ名 | 型 | 設定内容 |
|---|---|---|
| タスク | リレーション | タスクDB（双方向ON） |
| 議事録 | リレーション | 議事録DB（双方向ON） |
| 未完了タスク数 | ロールアップ | リレーション`タスク` → プロパティ`状態` → 計算`未チェックの数`…ではなく、下の数式を使う（後述） |
| 最終打合せ日 | ロールアップ | リレーション`議事録` → プロパティ`日付` → 計算`最新の日付` |
| 停滞日数 | 数式 | `dateBetween(now(), prop("最終打合せ日"), "days")` |
| 停滞アラート | 数式 | 下記コード参照 |

#### 「未完了タスク数」の作り方

`状態` はセレクト型のためロールアップの単純カウントでは絞り込めない。以下のどちらかを選ぶ。

- **簡単な方法**：タスクDBに `完了フラグ`（チェックボックス）を追加し、
  ロールアップ`タスク` → `完了フラグ` → 計算`未チェックの数`
- **数式を使う方法**：ロールアップで `状態` を「元の値」として取得し、
  数式側で `"完了"` 以外を数える

初期構築では**簡単な方法**を推奨する。

#### 「停滞アラート」の数式

```
if(
  empty(prop("最終打合せ日")),
  "⚪️ 記録なし",
  if(
    and(
      dateBetween(now(), prop("最終打合せ日"), "days") > 14,
      not(contains("実施済 請求済 完了 失注", prop("ステータス")))
    ),
    "🔴 停滞",
    "🟢 正常"
  )
)
```

> 最終打合せから15日以上経過し、かつ案件がまだ終わっていない場合に 🔴 が立つ。
> 「動いていない案件」が一覧上で自動的に浮かび上がる。

### CSV に含まれる列

| プロパティ名 | 型 | 備考 |
|---|---|---|
| タスク名 | タイトル | 動詞で終える（「〜の作成」「〜の確認」） |
| 案件 | テキスト → **リレーション** | |
| 担当者 | テキスト → ユーザー（任意） | |
| 期限 | 日付 | |
| 状態 | テキスト → **ステータス** | 未着手 / 進行中 / 完了 / 保留 |
| 種別 | テキスト → **セレクト** | 提案書作成 / 見積 / 教材準備 / 会場手配 / 講師アサイン / 請求 / その他 |
| メモ | テキスト | |

### インポート後に追加

| プロパティ名 | 型 | 設定内容 |
|---|---|---|
| 完了フラグ | チェックボックス | 案件DBの「未完了タスク数」用。完了時にチェック |
| 期限切れ | 数式 | `and(prop("期限") < now(), not(prop("完了フラグ")))` |

## ④ 議事録DB

### CSV に含まれる列

| プロパティ名 | 型 | 備考 |
|---|---|---|
| タイトル | タイトル | 命名規則 `YYYY-MM-DD_相手先_目的` |
| 案件 | テキスト → **リレーション** | 案件に紐づかない全社会議などは空欄でよい |
| 日付 | 日付 | |
| 種別 | テキスト → **セレクト** | 下表参照 |
| 参加者(社内) | テキスト → マルチセレクト（任意） | |
| 参加者(先方) | テキスト | |
| 決定事項サマリー | テキスト | 本文を読まなくても要点が分かる1〜2行 |
| 未決事項 | セレクト | あり / なし |

### 種別の選択肢

| 選択肢 | 用途 |
|---|---|
| クライアント商談 | 提案・受注前のやり取り |
| 事前打合せ | 受注後、実施前の詳細詰め |

| 実施後振り返り | 研修実施直後の所感・改善点 |
| 講師打合せ | 講師との内容すり合わせ |

## 補足：社内MTGと社外MTGでDBを分けるべきか

**分けないことを推奨する。**（1つの議事録DB＋`種別`プロパティ＋ビューで切り替える）

| 理由 | 説明 |
|---|---|
| 検索の一元化 | 今回の導入目的そのもの。DBを分けると「あの話どこだっけ」が再び2箇所探しになる |
| リレーションが1本で済む | 案件ページに社内・社外の議事録が**時系列で混ざって**並ぶ。これが実は最も文脈を追いやすい |
| 集計が単純 | 「最終打合せ日」のロールアップが1つで済む。2DBだと二重集計になり数式が複雑化する |

**例外：機密度で分ける場合のみ別DBにする。**
役員会議・人事評価・M&A など、案件と無関係かつ閲覧範囲を厳格に限定すべき議事録は、
Business プランの**非公開チームスペース**に別DBとして置く。
分割の軸は「社内/社外」ではなく「機密度」である点に注意。
