# 全社SharePoint 再構築 — 全体設計方針

## 0. 前提（未確認のためこの前提で設計。違えば該当箇所を修正します）

| # | 前提 | 影響範囲 |
|---|---|---|
| P1 | 全社員が Microsoft 365（SharePoint/Teams/Forms）ライセンスを保有 | 全体 |
| P2 | Entra ID に `department`（部）が人事データから同期されている | 権限設計（動的グループ） |
| P3 | Entra ID P1 以上を保有（動的グループが使える） | 権限設計。無い場合は静的グループ＋手運用 |
| P4 | Power Automate Premium（Notion コネクタ／HTTP アクション）が使える | 問合せ→Notion 連携 |
| P5 | 全社員が Notion のメンバーアカウントを持つ（または持たせられる） | 「全社員が進捗を見れる」要件 |
| P6 | 業務委託者は Entra ゲストユーザーとして招待する（社内アカウントは発行しない） | ビジネスパートナーサイト |
| P7 | 各部の「課」は最大2〜3課 | ライブラリ数・グループ数 |

> P4・P5 が満たせない場合の代替案は `03_問合せ統一_Notion連携設計.md` の「代替案」に記載。

## 1. 元案からの変更点（ここが設計の肝）

### 変更1: 「WorkBase 配下のサブサイト」ではなく「ハブサイト＋独立サイト」にする

元案の階層図はサブサイト構造に見えます。サブサイトは使わないでください。

| | サブサイト | ハブサイト＋独立サイト（推奨） |
|---|---|---|
| 組織改編時の移動 | ほぼ不可能（URL 固定・切り離せない） | ハブの紐づけを変えるだけ／数クリック |
| 権限 | 親から継承。切ると破綻しやすい | サイト単位で完全独立 |
| 容量・保持ポリシー | 親と一蓮托生 | サイト単位で設定可 |
| 廃止・アーカイブ | 親ごとでないと消せない | サイト単位でアーカイブ可 |

**構成**
- `WorkBase` = ハブサイト（コミュニケーションサイト）。全社の入口・共通ナビゲーション・全社お知らせ・全社マニュアル。
- 配下の10サイトはすべて**独立したサイトコレクション**を作り、WorkBase ハブに関連付ける。
- `ビジネスパートナー` は **WorkBase ハブに関連付けない**（別ハブ、または単独サイト）。ナビが混ざると誤って社外秘リンクを露出させます。

### 変更2: 公開/非公開は「ページ」ではなく「ドキュメントライブラリ」で分ける

元案の `【公開ドキュメント】TOP` `【非公開ドキュメント】部限定` は**ページ**として書かれていますが、SharePoint のページには権限で守る力がほぼありません（検索・直リンク・共有リンクで中身に到達できてしまう）。

- **ページ** = 案内・説明・リンク集・体制図（＝読み物）
- **ドキュメントライブラリ** = 実ファイル（＝守る対象）

したがって、部サイトの中身はこう読み替えます。

| 元案 | 実体 |
|---|---|
| 【公開ドキュメント】TOP | 部サイトのホームページ内の1セクション（ページを1枚増やす必要なし） |
| 【公開ドキュメント】➀課 / ②課 | ライブラリ `01_公開_➀課` `01_公開_②課`（全社閲覧可）＋ 課の案内ページ |
| 【非公開ドキュメント】部限定 | ライブラリ `02_限定_部` （部メンバーのみ） |
| 【非公開ドキュメント】➀課限定 / ②課限定 | ライブラリ `02_限定_➀課` `02_限定_②課`（課メンバーのみ） |

**鉄則: 一意の権限はライブラリ単位まで。フォルダ単位・ファイル単位の個別権限は禁止。**
（個別権限を許すと、半年で誰も権限の全体像を説明できなくなります。組織改編のたびに棚卸し不能になる最大の原因です。）

### 変更3: 問合せ Forms は部署ごとに作らず、全社1本＋分岐にする

理由は `03_問合せ統一_Notion連携設計.md` に記載。

## 2. サイト一覧と URL

**URL には部署名を入れない。** 組織改編で部署名が変わっても URL は変えない（URL 変更はリンク切れ・Teams のファイルタブ切れを大量発生させます）。表示名とナビゲーションだけ変えれば追随できます。

### 【社外秘エリア】WorkBase ハブ

| 表示名 | URL | サイト種別 | 責任部署 | 既定の閲覧範囲 |
|---|---|---|---|---|
| WorkBase（ハブ） | `/sites/workbase` | コミュニケーション | 管理部 | 全社員 |
| knowledge | `/sites/wb-knowledge` | コミュニケーション | 管理部 | 全社員 |
| 社長室 | `/sites/wb-exec` | チーム（プライベート） | 社長室 | 全社員（公開ライブラリのみ） |
| 法人事業部 | `/sites/wb-div01` | チーム（プライベート） | 法人事業部 | 全社員（公開ライブラリのみ） |
| スクール事業部 | `/sites/wb-div02` | チーム（プライベート） | スクール事業部 | 同上 |
| 研修・講師統括部 | `/sites/wb-div03` | チーム（プライベート） | 研修・講師統括部 | 同上 |
| デジタル開発部 | `/sites/wb-div04` | チーム（プライベート） | デジタル開発部 | 同上 |
| 管理部 | `/sites/wb-div05` | チーム（プライベート） | 管理部 | 同上 |
| 正本置き場 | `/sites/wb-records` | コミュニケーション | **管理部（運用）／各部（内容）** | 全社員（読み取り専用） |
| 案件管理 | `/sites/wb-projects` | チーム（プライベート） | **法人事業部（主管）／デジタル開発部（仕組み）** | 全社員（案件成果物のみ） |

### 【関係者外秘エリア】

| 表示名 | URL | サイト種別 | 責任部署 | 閲覧範囲 |
|---|---|---|---|---|
| ビジネスパートナー | `/sites/bp-portal` | チーム（プライベート） | スクール事業部 | 社員＋招待した業務委託者（ゲスト） |

> `wb-div01`〜`05` の連番は「現時点の部の並び」であり意味を持たせません。将来 `wb-div06` を足すだけで部の増設に対応できます。

### 「未定」2サイトの責任部署（提案）

- **正本置き場**: 管理部＝運用管理者（版管理ルール・レビュー期限の督促・アクセス権）／各規程の**内容オーナーは各部**。文書管理は「置き場の管理」と「中身の責任」を分けないと機能しません。
- **案件管理**: 法人事業部＝主管（案件定義・運用ルール）／デジタル開発部＝仕組み担当（ライブラリ構成・Notion 連携・自動化）。
  ただし着手前に**「案件」の定義を全社で1つに合意**してください。法人案件・スクール案件・研修案件で粒度が違うまま器だけ作ると必ず形骸化します。

## 3. 権限設計

### 3.1 グループ設計（Entra ID セキュリティグループ）

**個人をサイトの権限に直接追加しない。必ずグループ経由。** これを守れば、組織改編は「人事データの更新」だけで権限が追随します。

| グループ名 | 種別 | メンバーシップ |
|---|---|---|
| `SG-ALL-Employees` | 動的 | `user.userType -eq "Member"` かつ 在籍中 |
| `SG-DIV01` … `SG-DIV05` | 動的 | `user.department -eq "法人事業部"` 等 |
| `SG-DIV01-SEC01` 等（課） | 動的 or 手動 | `user.extensionAttribute1`（課コード）で判定。人事側に課コードが無ければ当面は手動 |
| `SG-EXEC` | 手動 | 社長室メンバー |
| `SG-BP-Partners` | 手動 | 業務委託者（ゲスト） |
| `SG-OWNER-<サイト>` | 手動 | 各サイトのオーナー（**必ず2名以上**） |

> `Everyone except external users`（全社員クレーム）は便利ですが、棚卸し時に「誰が見えるか」を説明しづらいので `SG-ALL-Employees` に統一することを推奨します。

### 3.2 権限マトリクス（部サイトの標準形）

| 対象 | SG-ALL-Employees | SG-DIVxx（部） | SG-DIVxx-SECyy（課） | SG-OWNER |
|---|---|---|---|---|
| サイト（ページ・ナビ） | 閲覧 | 編集 | 編集 | フル |
| `01_公開_共通` | 閲覧 | 編集 | 編集 | フル |
| `01_公開_➀課` | 閲覧 | 編集 | 編集 | フル |
| `02_限定_部` | **なし** | 編集 | 編集 | フル |
| `02_限定_➀課` | **なし** | 閲覧 | 編集 | フル |
| `02_限定_②課` | **なし** | 閲覧 | 編集 | フル |

- 「部限定」を部長だけでなく部メンバー全員が編集できる形にしています。ここを絞りすぎると、結局 Teams のチャットにファイルが散ります。
- `02_限定_➀課` を **部メンバーは閲覧可** にするか **完全非表示** にするかは経営判断です。ここだけは決めてください（人事評価・個人情報を扱う課があるなら非表示）。

### 3.3 秘密度ラベル（Microsoft Purview）

サイト（コンテナ）とファイルの両方にラベルを適用し、**設定ミスではなくラベルで守る**形にします。

| ラベル | 適用先 | 外部共有 | 非管理デバイス |
|---|---|---|---|
| 社内限定 | knowledge / WorkBase | 不可 | 制限付き Web のみ |
| 社外秘 | 各部サイト / 正本置き場 / 案件管理 | 不可 | 制限付き Web のみ |
| 関係者外秘 | ビジネスパートナー | **新規＆既存ゲスト可** | 制限付き Web のみ |

さらにテナント既定の外部共有を「既存のゲストのみ」にし、`bp-portal` だけサイト単位で緩めるのが安全です（既定を緩くして個別に締める運用は必ず漏れます）。

## 4. 命名規則

### サイト・ライブラリ
- ライブラリ名は全部署で**完全に同一の並び**にする（迷子をなくすため）。
  - `01_公開_共通` / `01_公開_➀課` / `01_公開_②課` / `02_限定_部` / `02_限定_➀課` / `02_限定_②課`
- 先頭の数字は並び順の固定用。名称の頭に「公開／限定」が来ることで、共有時の事故を減らします。

### フォルダ
- **深さは2階層まで。** それ以上はメタデータ列で表現する。
- 第1階層は「年度」または「業務カテゴリ」のどちらか一方に統一（部ごとに選択、混在禁止）。

### ファイル
`YYYYMMDD_文書種別_件名_v1.0.xxx`
例: `20260401_議事録_法人事業部定例_v1.0.docx`

### メタデータ列（全ライブラリ共通で持たせる）

| 列名 | 種類 | 用途 |
|---|---|---|
| 文書種別 | 選択肢 | 規程／マニュアル／帳票／議事録／提案書／報告書／その他 |
| 対象年度 | 選択肢 | 2026 / 2027 … |
| 機密区分 | 選択肢 | 社内限定／社外秘／関係者外秘 |
| 内容オーナー | ユーザー | 中身に責任を持つ人（作成者とは限らない） |
| 見直し期限 | 日付 | この日を過ぎたら棚卸し対象。**正本置き場では必須** |

## 5. SharePoint / Teams / Notion の役割分担

これを曖昧にしたままだと、どのツールを作り込んでも情報は散ります。

| | 置くもの | 置かないもの |
|---|---|---|
| **SharePoint** | 確定したファイル、正本、成果物、規程、マニュアル、部署の案内ページ | 進行中のタスク、議論、日程調整 |
| **Teams** | 会話、相談、日々のやりとり、会議 | 正本ファイル（チャットに添付しない。SharePoint のリンクを貼る） |
| **Notion** | タスク・依頼・案件の**進捗**、期限、担当、ステータス | 大容量ファイル、正本（SharePoint リンクを貼る） |

**判断基準の一言ルール**: 「これは**残す**ものか、**進める**ものか、**話す**ものか」
残す＝SharePoint／進める＝Notion／話す＝Teams。

## 6. 運用ルール（最低限これだけは決める）

1. 各サイトに**オーナー2名以上**を置く（1名だと異動・退職で管理不能になる）。
2. サイトは**申請制**。新規サイトは管理部が「サイトカルテ」の提出を受けて作成する（`02_サイト別コンテンツ定義.md` のテンプレート）。
3. 個別権限（フォルダ・ファイル単位）は原則禁止。必要な場合は管理部の承認と台帳記録を必須にする。
4. **年1回（4月）の棚卸し**: サイトカルテの見直し、権限グループの確認、`見直し期限` 超過ファイルの処理。
5. 外部共有リンクは**期限付き（最長30日）**を既定にする。
6. 廃止サイトは即削除せず「読み取り専用 → 90日後アーカイブ」の2段階にする。
