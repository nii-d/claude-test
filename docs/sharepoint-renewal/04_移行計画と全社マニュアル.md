# 移行計画と全社マニュアルの作り方

## 1. 「一つの資料にまとめる」の実装方法

やりたいことは「各サイトに何が書かれているかを一つの資料にまとめて全社展開」ですが、
**Word や PowerPoint で1本の資料を作ると、3か月で実態と乖離します。** サイトは変わり続けるからです。

### 推奨: 「サイトカルテ リスト」＋「マニュアルページ」の2階建て

```
[各部が更新]                    [自動表示]                 [全社が読む]

SharePoint リスト        →     リスト Web パーツ      →    全社マニュアル
「サイトカルテ台帳」            （フィルタ・検索可）         （WorkBase 上のページ）
 1サイト = 1行                                              ＋ PDF エクスポート（年1回）
```

- 各部は**自分の行を更新するだけ**。資料の取りまとめ作業が発生しない。
- 全社マニュアルのページは、固定の解説文＋リスト Web パーツ（台帳の埋め込み）で構成する。
- 監査や新入社員配布用に紙が要るときだけ、年1回 PDF 化する。

### サイトカルテ台帳リストの列

`WorkBase` サイトに作成。

| 列名 | 型 |
|---|---|
| サイト名 | 単一行テキスト（タイトル） |
| URL | ハイパーリンク |
| エリア | 選択（社外秘／関係者外秘） |
| 責任部署 | 選択 |
| サイトオーナー | ユーザー（複数） |
| 目的 | 複数行テキスト |
| 想定読者 | 選択（複数） |
| 秘密度ラベル | 選択 |
| 置くもの | 複数行テキスト |
| 置かないもの | 複数行テキスト |
| ライブラリ構成 | 複数行テキスト |
| 問合せ窓口 | ハイパーリンク |
| 最終棚卸し日 | 日付 |
| 次回見直し期限 | 日付 |

権限: 全社員 閲覧／各部オーナー 自分の行のみ編集（またはリスト全体編集＋変更履歴で牽制）

## 2. 全社マニュアル 目次案

`WorkBase` サイトのページとして作成し、`正本置き場 / 03_全社マニュアル` から正本版をリンク。

```
第1章 このマニュアルについて
  1.1 目的と対象読者
  1.2 更新ルールと問合せ先

第2章 情報の置き場所（最重要・ここだけは全員読む）
  2.1 SharePoint / Teams / Notion / OneDrive の使い分け
      → 「残す・進める・話す」の1行ルール
  2.2 迷ったときの判定フローチャート
  2.3 やってはいけないこと（チャットに正本を添付する／個人フォルダに正本を置く 等）

第3章 サイト全体像
  3.1 エリア構成（社外秘 / 関係者外秘）
  3.2 WorkBase ハブと全サイト一覧  ← サイトカルテ台帳を埋め込み
  3.3 サイトの探し方・検索のコツ

第4章 各サイトの使い方
  4.1 WorkBase（全社トップ）
  4.2 knowledge
  4.3 社長室
  4.4 各部サイト（共通の構成説明 ＋ 部ごとの差分）
  4.5 正本置き場
  4.6 案件管理
  4.7 ビジネスパートナー（関係者外秘の取扱い）

第5章 権限とセキュリティ
  5.1 公開ライブラリと限定ライブラリ
  5.2 共有リンクの発行ルール（期限付き・社外共有の可否）
  5.3 秘密度ラベルの意味と付け方
  5.4 業務委託者への情報提供ルール
  5.5 事故が起きたときの連絡先

第6章 ファイルの扱い方
  6.1 命名規則
  6.2 フォルダとメタデータ（深さは2階層まで）
  6.3 バージョン管理と正本の考え方
  6.4 保持期間と廃棄

第7章 依頼・問合せのしかた
  7.1 3つの行き先（調べる / 相談する / 依頼する）
  7.2 依頼 Forms の書き方（良い依頼・悪い依頼の例）
  7.3 進捗の見方（Notion / 進捗ボード）
  7.4 標準リードタイム表

第8章 部署別クイックリファレンス
  各部 1ページ: 役割 / 何を頼めるか / 何は頼めないか / 窓口 / リードタイム

第9章 FAQ・困ったとき
付録A 用語集
付録B サイトカルテ様式
付録C 変更履歴
```

**第2章と第7章だけは全社員必読**にし、他は逆引きで使う想定にしてください。全章を読ませようとすると誰も読みません。

## 3. 移行（リセット）の進め方

### Phase 0: 準備（〜1か月）
- [ ] 本設計の合意（特に「決めるべきこと」→ 5章）
- [ ] 新組織の部・課の確定（**これが決まらないと権限グループが作れない**）
- [ ] 現行サイトの棚卸し
- [ ] Entra グループ・秘密度ラベルの設計と作成

**現行サイト棚卸しシート**

| サイト名 | URL | 容量 | 最終更新 | 管理者 | 判定 | 移行先 |
|---|---|---|---|---|---|---|
| | | | | | 移行／正本化／アーカイブ／廃棄 | |

判定の基準:
- **移行**: 直近1年でアクセスがあり、今後も使う
- **正本化**: 規程・様式 → 正本置き場へ（内容の確認と版の確定が必要）
- **アーカイブ**: 使わないが法定保存・監査で必要 → 読み取り専用で保管
- **廃棄**: 保持期間を過ぎている

> **全部を移行しようとしないでください。** リセットの最大の価値は「捨てること」です。目安として、移行するのは全体の3割以下です。

### Phase 1: 器を作る（2〜3週）
- [ ] WorkBase ハブ作成、10サイト作成、ハブ関連付け
- [ ] 標準ライブラリ・メタデータ列・ページのテンプレート適用（**サイトテンプレート機能で全部署に一括適用**。手作業でやると必ず揺れます）
- [ ] 権限グループの割当、秘密度ラベル適用
- [ ] ビジネスパートナーサイトを別途作成（ハブ非関連付け・外部共有設定）

### Phase 2: 中身を決める（3〜4週）
- [ ] 各部がサイトカルテを記入（テンプレートは `02_` を配布）
- [ ] 管理部がレビュー（**「置かないもの」が書かれているかを重点確認**）
- [ ] 各部サイトのホームページ作成（問合せブロック含む）

### Phase 3: 移行（4〜6週）
- [ ] 判定「移行」のファイルを新サイトへ（SharePoint 移行ツール／Migration Manager）
- [ ] 移行時に命名規則・メタデータを付与（**移行後にやると絶対にやりません**）
- [ ] 正本の確定作業（各部の内容オーナーが「これが最新」を宣言）

### Phase 4: 切替（1週）
- [ ] 全社説明会（第2章・第7章の内容）
- [ ] 旧サイトを**読み取り専用**に変更＋トップに移行先の案内バナー
- [ ] 新サイトを全社公開、Teams のファイルタブ・お気に入りの張り替え案内

### Phase 5: 定着（切替後3か月）
- [ ] 週次で「旧サイトへのアクセス数」を確認（減らなければ移行漏れがある）
- [ ] 1か月後: 依頼データを見て FAQ 更新
- [ ] 3か月後: 旧サイトをアーカイブ（Microsoft 365 Archive）
- [ ] 以後: 年1回（4月）の棚卸しを定例化

## 4. 組織改編に強くしておくための仕込み

再構築が「今回限り」で終わらないよう、次の改編で困らない形にしておきます。

| 仕込み | 効果 |
|---|---|
| サイト URL に部署名を入れない | 改編で URL 変更＝大量リンク切れが起きない |
| 権限は動的グループ（`user.department`）経由 | 人事データ更新だけで権限が追随。手作業ゼロ |
| ライブラリ名を全部署共通に固定 | 部が増減しても構成が揺れない |
| ハブ関連付けで階層を表現 | 部の統廃合は関連付けの付け替えだけ |
| Forms は1本＋選択肢 | 部の増減は選択肢の追加/削除のみ |
| サイトカルテを台帳（リスト）で管理 | マニュアルの作り直しが不要。行の更新だけ |

## 5. 決めるべきこと（設計を確定させるために回答が必要）

| # | 論点 | 未決だと困ること | 提案 |
|---|---|---|---|
| 1 | 新組織の**課**の正式名称と数 | 権限グループ・ライブラリ数が確定しない | 早期確定を最優先 |
| 2 | Entra に**課**の属性があるか | 動的グループが課レベルで作れない | 人事側に課コード列の追加を依頼 |
| 3 | `02_限定_➀課` を**部メンバーに見せるか** | 権限マトリクスが確定しない | 原則見せる。人事情報を扱う課のみ非表示 |
| 4 | **全社員に Notion ライセンスを配るか** | 「全社員が進捗を見れる」が実現しない | 配らないなら `03_` の代替案A（SharePoint リスト） |
| 5 | **Power Automate Premium** の保有状況 | Notion 連携が実装できない | フローごとプラン3本で足りる |
| 6 | 業務委託者は**ゲスト**か社内アカウントか | BP サイトの外部共有設計が変わる | ゲスト推奨（棚卸ししやすい） |
| 7 | 「**案件**」の定義と案件コードの採番 | 案件管理サイトが機能しない | 法人事業部主管で先に合意 |
| 8 | Teams チャネル問合せを**残すか** | 導線ルールが確定しない | 残す。ただし依頼は Forms へ代理起票 |
| 9 | 旧サイトの**保持期間** | 移行判定ができない | 読み取り専用3か月 → アーカイブ |
| 10 | 秘密度ラベルの**適用範囲**（Purview のライセンス） | ラベルでの保護ができない | E3 なら手動ラベル、E5 なら自動ラベル |

**1・4・5 の3つが最優先です。** これが決まらないと、権限設計と Notion 連携の実装可否が確定しません。
