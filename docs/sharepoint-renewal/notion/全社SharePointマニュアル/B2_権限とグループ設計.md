# B2 権限とグループ設計

**誰向け**: 情シス、デジタル開発部、管理部
**所要時間**: 8分
**この章の結論**: 個人をサイトに直接追加しない。すべて動的グループ経由にすれば、組織改編は人事データの更新だけで追随する。

---

## 原則: 個人を権限に直接追加しない

**すべての権限付与はグループ経由で行います。** これを守れば、組織改編時にやることは「人事データの更新」だけになります。個人を直接追加すると、改編のたびに全サイトを手作業で棚卸しすることになります。

## グループ設計（Entra ID セキュリティグループ）

| グループ名 | 種別 | メンバーシップの決め方 |
|---|---|---|
| `SG-ALL-Employees` | 動的 | `user.userType -eq "Member"` かつ在籍中 |
| `SG-DIV01` 〜 `SG-DIV05` | 動的 | `user.department -eq "法人事業部"` など |
| `SG-DIV01-SEC01` など（課） | 動的または手動 | 課コード属性で判定。人事側に課コードがなければ当面は手動 |
| `SG-EXEC` | 手動 | 社長室メンバー |
| `SG-BP-Partners` | 手動 | 業務委託者（ゲスト） |
| `SG-OWNER-<サイト名>` | 手動 | 各サイトのオーナー（**必ず2名以上**） |

### 動的グループについて

- 動的グループの利用には **Entra ID P1 以上**が必要です。保有状況を確認してください。
- P1がない場合は静的グループになり、組織改編時に手作業での入れ替えが発生します。
- 部レベル（`user.department`）は人事データから同期されている前提です。**課レベルの属性がない場合は、人事側に課コード列の追加を依頼してください。** これがないと課単位の権限を自動化できません。

### `Everyone except external users` を使わない理由

「全社員」を表す組み込みのクレームは便利ですが、棚卸しのときに「結局誰が見られるのか」を説明しづらくなります。`SG-ALL-Employees` に統一し、メンバーシップを明示的に管理してください。

## 権限マトリクス（部サイトの標準形）

| 対象 | SG-ALL-Employees | SG-DIVxx（部） | SG-DIVxx-SECyy（課） | SG-OWNER |
|---|---|---|---|---|
| サイト（ページ・ナビ） | 閲覧 | 編集 | 編集 | フルコントロール |
| `01_公開_共通` | 閲覧 | 編集 | 編集 | フルコントロール |
| `01_公開_➀課` | 閲覧 | 編集 | 編集 | フルコントロール |
| `01_公開_②課` | 閲覧 | 編集 | 編集 | フルコントロール |
| `02_限定_部` | 権限なし | 編集 | 編集 | フルコントロール |
| `02_限定_➀課` | 権限なし | 閲覧 | 編集 | フルコントロール |
| `02_限定_②課` | 権限なし | 閲覧 | 編集 | フルコントロール |

### 設計の意図

- **`02_限定_部` は部長だけでなく部メンバー全員が編集できます。** ここを絞りすぎると、結局ファイルがTeamsのチャットに散ります。
- **`02_限定_➀課` を部メンバーが閲覧できるか**は経営判断です。既定は「閲覧できる」にしています。
- **管理部だけは例外**です。人事評価・給与・労務相談・健康情報を扱うため、課限定ライブラリを部メンバーにも見せません。

## サイト別の閲覧範囲

| サイト | 全社員が閲覧できる範囲 | 特記事項 |
|---|---|---|
| WorkBase | すべて | |
| knowledge | すべて | 全社員がページを投稿できる（管理部が承認） |
| 社長室 | 公開ライブラリのみ | `02_限定_部` は社長室メンバーのみ。他部署の部長も見られない |
| 部サイト × 5 | 公開ライブラリのみ | 管理部のみ課限定を部メンバーにも非公開 |
| 正本置き場 | すべて（**閲覧のみ**） | 編集は管理部のみ。全社員に編集権を配ると正本でなくなる |
| 案件管理 | 公開ライブラリのみ | 限定ライブラリは案件関係部署のみ |
| ビジネスパートナー | 招待された人のみ | `SG-BP-Partners` 経由 |

## 秘密度ラベル（Microsoft Purview）

設定ミスではなくラベルで守る形にします。サイト（コンテナ）とファイルの両方に適用します。

| ラベル | 適用するサイト | 外部共有 | 非管理デバイス |
|---|---|---|---|
| 社内限定 | WorkBase / knowledge | 不可 | 制限付きWebのみ |
| 社外秘 | 各部サイト / 社長室 / 正本置き場 / 案件管理 | 不可 | 制限付きWebのみ |
| 関係者外秘 | ビジネスパートナー | 新規ゲスト・既存ゲストとも可 | 制限付きWebのみ |

**テナント既定の外部共有は「既存のゲストのみ」に絞り、ビジネスパートナーサイトだけをサイト単位で緩めてください。** 既定を緩くして個別に締める運用は必ず漏れます。

> ラベルによる自動適用には Purview のライセンス条件があります。E3 では手動ラベル、E5 では自動ラベルが使えます。保有状況を確認してください。

## 運用ルール

1. 各サイトに**オーナーを2名以上**置く。1名だと異動・退職で管理不能になります。
2. 新規サイトは**申請制**。管理部がサイトカルテの提出を受けて作成します。
3. **個別権限は原則禁止**（B1 決定5）。必要な場合は管理部の承認と台帳記録を必須にします。
4. 外部共有リンクは**期限付き（最長30日）**を既定にします。
5. **年1回（4月）の棚卸し**で、権限グループとサイトカルテを見直します。
6. ビジネスパートナーサイトのゲストは**四半期ごと**にアクセスレビューを行います。

## 組織改編が起きたときの手順

1. 人事データで `user.department` を更新する（動的グループが自動で追随）
2. 部の名称が変わった場合、**サイトの表示名とハブナビゲーションだけ**を変更する（URLは変えない）
3. 部が統合された場合、ハブの関連付けを外し、ライブラリを統合先サイトへ移動する
4. 部が新設された場合、サイトテンプレートから新サイトを作り、`SG-DIV06` を作成してハブに関連付ける
5. サイトカルテ台帳の該当行を更新する
