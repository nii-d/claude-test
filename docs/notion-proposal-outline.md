## 0. この構成案の前提

### 確定している情報

| 項目 | 内容 |
|---|---|
| 事業 | 企業向け教育研修の提供 |
| 案件規模 | 年間約1,000件（問い合わせベース） |
| 1案件の関与者 | 営業1〜2名 / 運営管理1〜2名 / 講師管理1名 / 講師1〜2名 + 機材部門・コンテンツ部門と連携 + PMO1名 |
| 組織の転機 | PMO部署と人事組織が同時に新設される |
| 現行ツール | Microsoft 365（Teamsのグループチャット中心） |
| 既定路線 | コミュニケーションはパブリックチーム／チャネル運営に変更予定（Notion導入とは独立して実施） |
| 他ツール | システム開発部はBacklogを運用中・継続 |
| 推進の力学 | 自社社長が最も強い推進者。上層部に明確な反対者なし |
| 真の関門 | ホールディングスの認可（恐らく情シス）。外部SaaS導入事例は不明 |
| 既存の実績 | 上層部で3か月のPoC実施済み（内容・結果は未把握） |

### 提案の基本設計

**主語を「Notion導入」にしない。**「PMO立ち上げに合わせた、案件管理と会議運営の標準化」を主語とし、Notionはその実行基盤として位置づける。承認対象を「ツール」ではなく「組織の仕組み」にすることで、決裁の性質が変わる。

**資料は2部構成にする。**

- **本編**（自社上層部向け）— 全社導入の意思決定と予算承認。社長が推進者である以上、説得ではなく「決裁の段取りを整える」文書
- **別添A**（ホールディングス／情シス向け）— セキュリティ審査を通すための資料。**実質的にはこちらが本体**。本編だけ作って情シスで止まるのが最も起きやすい失敗

### 意図的に使わないもの

| 使わないもの | 理由 |
|---|---|
| 助成金絡みの失敗事例 | 提案者の判断により除外 |
| 「週30〜40時間会議に出ている人がいる」 | 極端例として流される。平均値で語る |
| Backlogの親子・孫課題の階層論 | 経営層には粒度が細かすぎる。守りの材料としてのみ使う |

### S3. なぜ今なのか

**メッセージ**: PMOが立ち上がる今が、案件管理を標準化する唯一のタイミングです。

載せる要素:
- PMO新設が決定 → 案件管理の仕組みを組織として整える転機
- しかし現状、**PMOが使う「管制塔」が存在しない**
- 器のないままPMOを作ると、PMOは各部署にチャットと電話で状況を聞いて回る係になる

**話法メモ**: この最後の一行が本編で最も効く。「PMOを作ることは決まっている」という既成事実に乗せるので、反論の対象がNotionではなく「PMOという意思決定そのもの」になり、誰も反対できない構図になる。

図案（1案件の関与者を横並びで）:

        ├─ 運営管理 1〜2名

- 1案件あたり **のべ6〜8名** が関与
- これが **年間約1,000件**
- 現在この連携は、Teamsのグループチャットと個人管理のExcelで行われている

**話法メモ**: ここでは問題を語らず、事実だけを置く。数字の大きさが自然に「これは無理だ」と語ってくれる。

### S5. 現に起きていること

**メッセージ**: すでに、納期と品質に影響が出ています。

| 起きたこと | 何が失われたか |
|---|---|
| チャットで依頼した内容を運営担当が見逃し、期日が守られなかった | 納期 |

> **⚠ 作成時の注意**
> この3件は、書き方を誤ると特定の部署・個人の吊し上げになる。**部署名・個人名は絶対に書かない**。「担当者が見逃した」ではなく「見逃せてしまう仕組みだった」と、必ず主語を仕組みに置くこと。上層部への提案資料は社内に回覧されるため、ここを誤ると導入後に協力を得られなくなる。

### S6. なぜ起きるのか ― 3つの構造欠陥

**メッセージ**: 原因は3つあり、いずれも今のツールの使い方では解消できません。

| # | 欠陥 | 現状 | 結果 |
|---|---|---|---|
| 1 | **可視性がない** | グループチャットは招待された人しか見られない | 招待漏れ＝情報から遮断。PMOが横断把握できない |
| 2 | **記録が残らない** | 決定事項・担当・期日がチャットに流れる | 「言った/言わない」。後から追えない |
| 3 | **管理手法がない** | WBS・ガントが標準装備でなく、Excelで各自バラバラ | 案件間の比較も、全体の集計も不可能 |

**話法メモ**: 3つに整理して番号を振る。以降のスライドはこの1・2・3に対応させ、「S6で挙げた3つが、こう解決されます」という参照構造にすると聞き手が迷わない。

### S7. 会議に費やしている時間

**メッセージ**: 目的が曖昧な会議に、年間 **◯◯◯万円** 相当の人件費が消えています。

| 項目 | 値 | 出所 |
|---|---|---|
| 対象人数 | 100名 | 確定 |
| 1人あたり週の会議時間（平均） | **◯時間** | ⚠ 要実測 |
| うち目的が曖昧なものの割合 | 3〜4割 | 現場の体感 |
| 時間単価 | 約3,000円 | 平均年収450万 × 1.25 ÷ 1,900時間 |
| 年間換算 | **◯◯◯万円** | 上記の積 × 45週 |

> **⚠ この数字は必ず実測してから出すこと**
> 会議時間の平均値は、Microsoft 365 の **Viva Insights** または Teams の利用状況レポートから実データが取得できる。情シスに依頼すれば出せる可能性が高い。**体感値のまま金額を出すと、その一点を突かれて資料全体の信頼が落ちる。**
> 実測が間に合わない場合は「仮に平均◯時間とすると」と仮定であることを明示し、断定しない。

**話法メモ**: 「削減できる額」ではなく「投じている額」として提示する。全部が無駄なわけではないので、削減目標は控えめ（後述S12）に置く。

### S8. 打ち手 ― 「議事録を書く」ことが、そのまま案件管理になる

**メッセージ**: これが今回の提案の核心です。

図案:

```
  会議前            会議中・会議後              自動的に現れる場所
┌──────────┐      ┌──────────────┐      ┌────────────────────┐
│ アジェンダを │ ───→ │ 議事録を書く   │ ───→ │ ① 案件ページ        │
│ 事前に作る   │      │ 決定事項・ToDo │      │ ② 担当者のToDo一覧  │
│（目的の明確化）│      │ を項目として   │      │ ③ PMOの全案件ビュー │
└──────────┘      │ 登録する       │      └────────────────────┘
                    └──────────────┘         ※ すべて同じ実体
```

**Word・OneNote・Loop との決定的な違い**:

| | 議事録の正体 | 結果 |
|---|---|---|
| Word / OneNote / Loop | **文書**。決定事項もToDoも、文中に埋まった「文字」 | 転記しないと管理に使えない。転記されなければ消える |
| Notion | **データベースのレコード**。ToDoは案件に紐づいたタスクそのもの | 議事録を書いた時点で管理が完了している |

→ **二重入力が発生しない。** 「議事録を書く」という1つの行為が、そのままプロジェクト管理の入力になる。

**話法メモ**: 上層部が2つの要望（案件管理・会議改革）を「別々のお願い」と受け取ると、提案は弱くなる。このスライドは、**2つが1つの仕組みの表と裏であることを示す**ためにある。本編で最も時間をかけて説明すべき1枚。

### S9. Microsoft 365 では足りないのか（正面から答える）

**メッセージ**: 検討した結果、一部はM365で対応します。残りが今回のご相談です。

| やりたいこと | M365での解 | 判断 |
|---|---|---|
| チャットの可視化 | Teamsのパブリックチーム／チャネル | ✅ **Notionは不要。この方針で実施済み** |
| タスク・WBS・ガント | Planner（上位機能は追加ライセンス） | △ 案件情報・議事録とは別の場所に持つことになる |
| ストック情報 | Loop / SharePoint / OneNote | △ 文書であってデータではない。集計・横断が困難 |
| 一覧・台帳 | Lists | △ 議事録・ドキュメントと連動しない |

**結論**: すべてを満たそうとすると **Planner + Lists + Loop + SharePoint の併用**になる。その結果——

- 同じ情報を複数箇所に入力する **二重管理コスト**が発生する
- どれが最新かがわからなくなり、**結局チャットで聞くことになる**（現状に戻る）

**役割分担の明示**:

> **Teams = 会話する場所 / Notion = 記録し、管理する場所**

> **⚠ 数字の裏取り**
> Plannerの上位機能（ガント・依存関係）が追加ライセンスを要するかは、**提出前に必ず最新のライセンス体系を確認すること**。ここを誤ると情シスに即座に指摘される。

**話法メモ**: このスライドの価値は、**「M365で済む部分は済ませます」と正直に認めている点**にある。全否定すると「Notionを売り込みたいだけ」に見える。一部を譲ることで、残りの主張の信頼性が上がる。

### S10. Backlogがあるのに、なぜ別のツールが要るのか（守り）

**メッセージ**: 用途が違います。Backlogは継続して使います。

| | Backlog（システム開発部） | Notion（全社） |
|---|---|---|
| 対象 | 社内システムの改修課題 | 研修案件・議事録・社内ナレッジ |
| 使う人 | 開発メンバー | 全社員（営業・運営・講師管理・機材・コンテンツ・PMO） |
| 方針 | **現行のまま継続** | 新規導入 |

- システム開発部でBacklogが機能しているのは事実であり、置き換える提案ではない
- 開発課題の管理と、部門横断の案件管理は求められる構造が異なる

**話法メモ**: 攻めではなく守り。聞かれたら出す想定で、本編に置くか別添Bに回すかは当日の時間次第。**Backlogの階層構造（親子・孫課題）の話には踏み込まない**——技術的に細かすぎるうえ、「じゃあBacklogの機能追加を待てば？」という返しを招く。

### S15. 進め方

**メッセージ**: ライセンスは全社で取得し、業務の移行は段階的に行います。

| Phase | 時期 | 内容 |
|---|---|---|
| **Phase 0** | 承認後すぐ | ホールディングス／情シスへの申請・セキュリティ審査 |
| **Phase 1** | 審査通過後 1〜2か月 | **会議運用から開始**。アジェンダ・議事録の全社標準化（習得が容易で、効果が早く出る） |
| **Phase 2** | 3〜4か月目 | **案件管理を1部門で先行運用**。テンプレートを実案件で検証 |
| **Phase 3** | 5か月目以降 | 全案件へ展開。PMOの横断ビュー稼働 |

**なぜライセンスは全社なのか**（想定質問への先回り）:
> 案件は営業・運営管理・講師管理・機材・コンテンツと**部門をまたいで進みます**。一部の部署だけが使う状態では、結局その外側とはチャットでやり取りすることになり、二重管理が生まれます。**部分導入は、この課題に対しては機能しません。**

**話法メモ**: 「全社即導入」は費用と審査の両面でハードルが高い。しかし**ライセンス（全社）と業務移行（段階的）を分けて説明する**ことで、「いきなり全部やるのか」という不安を消しつつ、全社ライセンスの必要性は譲らない形にできる。

### S16. 成功の判定基準と、撤退基準

**メッセージ**: 効果が出なければ、1年で見直します。

**KPI（導入6か月後・12か月後に測定）**

| 指標 | 現状 | 目標 |
|---|---|---|
| 案件の期日遵守率 | 未計測 | 計測開始 → ◯% |
| 1人あたり週の会議時間 | ◯時間 | ▲◯% |
| 議事録が残っている会議の割合 | ◯% | 90%以上 |
| 案件情報がNotionに登録されている割合 | 0% | 95%以上 |

**撤退基準**: 導入12か月後、案件登録率が◯%を下回る場合は継続を再検討する。

**話法メモ**: **撤退基準を自分から示すのが、この資料で最も効く技術**。「効果がなければやめます」と言える提案者は信頼される。逆に、これを書かない提案は「言いっぱなし」に見える。

## 別添A: セキュリティ・ガバナンス（ホールディングス／情シス向け）

> **この別添の位置づけ**
> 自社の上層部は社長を筆頭に賛成の見込み。**実質的な関門はここ**。本編より先に、あるいは並行して準備を進めること。

### A-0. 最優先アクション

**提案の前に、情シスに「審査で何を求められるか」を聞きに行く。**

これが最も重要で、最も見落とされやすい。以下の3点を確認する:

1. 外部SaaS導入時の審査プロセスと、標準的な所要期間
2. 提出を求められる資料の一覧（チェックシートの様式があるはず）
3. 過去に承認された外部SaaSの事例（あれば、その水準に合わせられる）

**理由**: 審査基準がわからないまま資料を作ると、確実に手戻りする。また、事前に相談しておくと情シスが「敵」ではなく「一緒に通す側」になる。**これはコストではなく、審査期間を短縮する投資。**

### A-2. 運用面での安全設計（こちらから提示する）

審査を通しやすくするため、**制約を自分から課す**:

| 設計 | 内容 |
|---|---|
| 外部共有の原則禁止 | 公開リンクの生成を管理者権限で禁止。必要時のみ申請制 |
| 管理者の限定 | ワークスペース管理者は情シスとPMOの計◯名のみ |
| 扱わない情報の明示 | 個人情報・機密度◯以上の情報はNotionに保存しない旨をルール化 |
| 退職・異動時の手順 | アカウント削除とデータ移管の手順を事前に定義 |
| ログの定期確認 | PMOが月次で監査ログを確認 |

**話法メモ**: 「何でもできます」ではなく「**ここまでしか使いません**」と自ら線を引くほうが、審査は通りやすい。

### A-3. 想定される審査上の争点

- 「M365で完結できるのに、なぜ外部SaaSを増やすのか」 → 本編S9の内容で回答
- 「情報が社外サービスに置かれることのリスク」 → A-2の運用設計 + 扱わない情報の明示
- 「管理コストが増える」 → 管理者を限定、PMOが運用主体として明示

## 別添C: 数字の作り方（試算シート）

### C-1. 時間単価の算出

```
時間単価 = 平均年収 × 1.25（法定福利費等） ÷ 年間労働時間
        = 450万円 × 1.25 ÷ 1,900時間
        ≈ 2,960円 → 3,000円/時 として計算
```

※ 年収レンジは350万〜900万と幅があるため、**平均値で計算していることを注記する**。役員層が多く参加する会議のコストはこれより高くなるが、控えめに見せるため平均値を使う。

### C-2. 会議コスト

```
年間会議コスト = 100名 × 週◯時間 × 45週 × 3,000円
目的曖昧分     = 上記 × 35%（体感3〜4割の中央値）
削減見込み     = 目的曖昧分 × 30%（控えめに設定）
```

**⚠ 「週◯時間」は Viva Insights / Teams利用状況レポートで実測すること。**

### C-3. 手戻り・遅延コスト

```
年間損失 = 1,000件 × 遅延・手戻り発生率◯% × 1件あたり追加工数◯時間 × 3,000円
```

**⚠ 発生率と追加工数は実測が必要。** 過去半年の案件から数件をサンプル調査するのが現実的。**数字を作れない場合は、金額換算せず「S5の実例」の定性説明にとどめる**（無理な数字は突かれる）。
