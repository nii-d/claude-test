### 提案の基本設計

**主語を「Notion導入」にしない。**「PMO立ち上げに合わせた、案件管理と会議運営の標準化」を主語とし、Notionはその実行基盤として位置づける。承認対象を「ツール」ではなく「組織の仕組み」にすることで、決裁の性質が変わる。

**本編を3部構成として明示的に分ける。**

| 部 | 問い | 答えるべきこと |
|---|---|---|
| **第1部** | なぜ必要なのか | 弊社の課題は2つ（案件管理・会議）。それぞれNotionでこう解決する |
| **第2部** | なぜNotionなのか | M365でも他ツールでもなく、Notionである理由 |
| **第3部** | 導入すると何が起きるのか | 費用・効果・リスク・進め方・撤退基準 |

聞き手が「今どの話をされているのか」を見失わないよう、**各部の冒頭にセクション扉を置く**。

**資料全体は2部構成にする。**

- **本編**（自社上層部向け）— 全社導入の意思決定と予算承認。社長が推進者である以上、説得ではなく「決裁の段取りを整える」文書
- **別添A**（ホールディングス／情シス向け）— セキュリティ審査を通すための資料。**実質的にはこちらが本体**。本編だけ作って情シスで止まるのが最も起きやすい失敗

### 意図的に使わないもの

| 使わないもの | 理由 |
|---|---|
| 助成金絡みの失敗事例 | 提案者の判断により除外 |
| 「週30〜40時間会議に出ている人がいる」 | 極端例として流される。平均値で語る |
| Backlogの親子・孫課題の階層論 | 経営層には粒度が細かすぎる。守りの材料としてのみ使う |

## S5. なぜ今なのか

**メッセージ**: PMOが立ち上がる今が、仕組みを整える唯一のタイミングです。

## S6. 弊社の課題は、2つあります ★重要スライド

**メッセージ**: 性質の異なる2つの課題が、同時に存在しています。

**左右に並べる（この見せ方が今回の資料の骨格）**

|  | **課題A：案件管理** | **課題B：会議と議事録** |
|---|---|---|
| **何が起きているか** | 年間1,000件の研修案件が、部門をまたいで進むのに、進捗を一望する場所がない | 会議が多く、目的が曖昧なまま設定され、決定事項が後から追えない |
| **現在の管理方法** | Teamsのグループチャット ＋ 各自オリジナルのExcel | Teamsで会話 → AI議事録 → Word/OneNoteに保存 → リンクをチャットで共有 |
| **誰が困っているか** | 営業・運営管理・講師管理・機材・コンテンツ、そして新設のPMO | 全社員（特に会議時間の長い管理職層） |
| **放置するとどうなるか** | 納期遅延と手戻りが再発し、顧客の信用を損なう | 意思決定が遅れ、同じ議論が繰り返される |

**この2つは、後ほど1つの仕組みで解決できることをご説明します（S9・S10）**

**話法メモ**: **この資料で最も重要な1枚。** 2つの課題を最初に並べて宣言することで、以降のスライドがどちらの話をしているのかが明確になる。ここを飛ばして「Notionは便利です」と入ると、聞き手は最後まで論点を掴めない。

**視覚設計**: 左右2カラムを縦線で分ける。左をA（青系）、右をB（緑系）など色分けし、**以降のスライドでもこの色を一貫して使う**。聞き手は色で「今Aの話だ」と判断できる。

## S7. 課題A：案件管理 ― 何が起きているか

**メッセージ**: 年間1,000件が、部門横断で、チャットとExcelで動いています。

**（1）規模の実態**

```
        ┌─ 営業 1〜2名
        ├─ 運営管理 1〜2名
1案件 ──┼─ 講師管理 1名          ＋ 機材部門
        ├─ 講師 1〜2名           ＋ コンテンツ作成部門
        └─ PMO 1名（新設）
```

- 1案件あたり **のべ6〜8名** が関与し、**年間約1,000件**

**（2）現に起きたこと**

| 起きたこと | 失われたもの |
|---|---|
| チャットでの依頼を運営担当が見逃し、期日が守られなかった | 納期 |
| 教材開発の成果物が、期日になっても出てこない（部門間の温度感の差） | 納期・部門間の信頼 |
| 講師選定が遅れ、機材準備が間に合わなかった | 実施品質・顧客信用 |

**（3）なぜ起きるのか — 構造の問題**

| # | 欠陥 | 内容 |
|---|---|---|
| A-1 | 可視性がない | グループチャットは招待された人しか見られない。招待漏れ＝情報から遮断 |
| A-2 | 横断して見えない | Excelが各自バラバラ。案件間の比較も全体の集計も不可能 |
| A-3 | 管理手法がない | WBS・ガントが標準装備でなく、進捗と依存関係を追えない |

> **⚠ 作成時の注意**
> この3件は、書き方を誤ると特定の部署・個人の吊し上げになる。**部署名・個人名は絶対に書かない**。「担当者が見逃した」ではなく「見逃せてしまう仕組みだった」と、必ず主語を仕組みに置くこと。上層部への提案資料は社内に回覧されるため、ここを誤ると導入後に協力を得られなくなる。

## S8. 課題B：会議と議事録 ― 何が起きているか

**メッセージ**: 目的が曖昧な会議に、年間 **◯◯◯万円** 相当の人件費が消えています。

**（1）会議のコスト**

| 項目 | 値 | 出所 |
|---|---|---|
| 対象人数 | 100名 | 確定 |
| 1人あたり週の会議時間（平均） | **◯時間** | ⚠ 要実測 |
| うち目的が曖昧なものの割合 | 3〜4割（主に定例会議） | 現場の体感 |
| 時間単価 | 約3,000円 | 平均年収450万 × 1.25 ÷ 1,900時間 |
| 年間換算 | **◯◯◯万円** | 上記の積 × 45週 |

**（2）議事録の現状 — 情報が5か所を経由している**

```
Teams会議 → 文字起こし → AIで議事録生成 → Word化 → OneDriveに保存 → リンクをTeamsで共有
                                          └→ OneNoteにコピペ → リンクをTeamsで共有
```

- 保存先が人によって違い、**どこに何があるか分からない**
- チャットに流れたリンクは、時間が経てば遡れない
- **議事録は残っているのに、決定事項が追えない**

**（3）なぜ起きるのか — 構造の問題**

| # | 欠陥 | 内容 |
|---|---|---|
| B-1 | 目的が事前に定義されない | アジェンダを作る型がないため、「とりあえず集まる」定例が生き残る |
| B-2 | 決定が構造化されない | 決定事項・担当・期日が文章の中に埋もれ、検索も集計もできない |
| B-3 | 置き場所が分散する | Word / OneDrive / OneNote / Teams をまたぐたびに情報が流れていく |

> **⚠ 会議時間は必ず実測してから出すこと**
> 平均値は Microsoft 365 の **Viva Insights** または Teams の利用状況レポートから取得できる。情シスに依頼すれば出せる可能性が高い。**体感値のまま金額を出すと、その一点を突かれて資料全体の信頼が落ちる。**
> 実測が間に合わない場合は「仮に平均◯時間とすると」と仮定であることを明示し、断定しない。

**話法メモ**: 「削減できる額」ではなく「投じている額」として提示する。全部が無駄なわけではないので、削減目標は控えめ（S18）に置く。

## S9. Notionによる解決 ★重要スライド

**メッセージ**: 2つの課題は、それぞれこう解決されます。

**S6と同じ左右2カラムで、Before / After を並べる**

### 課題A：案件管理

| | Before | After |
|---|---|---|
| A-1 可視性 | 招待された人しか見えない | 全案件が誰からも見える |
| A-2 横断性 | Excelがバラバラで集計不能 | 全案件が同じ型。**PMOが1画面で1,000件を俯瞰** |
| A-3 管理手法 | 進捗と依存関係が追えない | ステータス・担当・期日が構造化され、遅延案件が自動で浮かび上がる |

### 課題B：会議と議事録

| | Before | After |
|---|---|---|
| B-1 目的 | とりあえず集まる定例が残る | **アジェンダを事前に書くことが型になる**。書けない会議は開かれなくなる |
| B-2 決定 | 文章に埋もれて追えない | 決定事項・担当・期日が項目として残り、検索・集計できる |
| B-3 置き場所 | Word/OneDrive/OneNote/Teamsに分散 | すべてNotionの1か所。案件からも人からも辿れる |

**話法メモ**: **B-1の「書けない会議は開かれなくなる」が、この提案の思想を最もよく表す一言。** ツールが会議を減らすのではなく、アジェンダを書くという行為が、目的のない会議を自然に淘汰する。ここは口頭で強調する。

## S10. そして、この2つは1つの仕組みで繋がります

**メッセージ**: 議事録を書くことが、そのまま案件管理の入力になります。

```
  会議前            会議中・会議後              自動的に現れる場所
┌──────────┐      ┌──────────────┐      ┌────────────────────┐
│ アジェンダを │ ───→ │ 議事録を書く   │ ───→ │ ① 案件ページ        │
│ 事前に作る   │      │ 決定事項・ToDo │      │ ② 担当者のToDo一覧  │
│（課題B の解決）│      │ を項目として   │      │ ③ PMOの全案件ビュー │
└──────────┘      │ 登録する       │      └────────────────────┘
                    └──────────────┘         （課題A の解決）
                                              ※ すべて同じ実体
```

- 会議で決まったToDoは、**転記せずにそのまま案件のタスクになる**
- 同じ実体が、案件ビューにも担当者のToDoにもPMOの横断ビューにも現れる
- **二重入力が発生しない**

**話法メモ**: S6で「2つの課題」と宣言し、S9で「それぞれ解決する」と示した上で、ここで初めて「実は1つの仕組みだった」と繋げる。**順番が重要**——最初から統合して語ると、聞き手はどちらの課題の話かを見失う。

## S12. Microsoft 365 では足りないのか

**メッセージ**: 検討した結果、一部はM365で対応します。残りが今回のご相談です。

| やりたいこと | M365での解 | 判断 |
|---|---|---|
| チャットの可視化 | Teamsのパブリックチーム／チャネル | ✅ **Notionは不要。この方針で実施します** |
| タスク・WBS・ガント（課題A） | Planner（上位機能は追加ライセンス） | △ 案件情報・議事録とは別の場所に持つことになる |
| ストック情報・議事録（課題B） | Loop / SharePoint / OneNote | △ 文書であってデータではない。集計・横断が困難 |
| 案件の一覧・台帳（課題A） | Lists | △ 議事録・ドキュメントと連動しない |

**結論**: すべてを満たそうとすると **Planner + Lists + Loop + SharePoint の併用**になる。その結果——

- 同じ情報を複数箇所に入力する **二重管理コスト**が発生する
- どれが最新かがわからなくなり、**結局チャットで聞くことになる**（＝現状に戻る）

**役割分担の明示**:

> **Teams = 会話する場所 / Notion = 記録し、管理する場所**

> **⚠ 数字の裏取り**
> Plannerの上位機能（ガント・依存関係）が追加ライセンスを要するかは、**提出前に必ず最新のライセンス体系を確認すること**。ここを誤ると情シスに即座に指摘される。

**話法メモ**: このスライドの価値は、**「M365で済む部分は済ませます」と正直に認めている点**にある。全否定すると「Notionを売り込みたいだけ」に見える。一部を譲ることで、残りの主張の信頼性が上がる。

## S13. Notionでなければならない一点

**メッセージ**: 議事録が「文書」ではなく「データ」であること。これが決定的な差です。

| | 議事録の正体 | 結果 |
|---|---|---|
| Word / OneNote / Loop | **文書**。決定事項もToDoも、文中に埋まった「文字」 | 転記しないと管理に使えない。転記されなければ消える |
| Notion | **データベースのレコード**。ToDoは案件に紐づいたタスクそのもの | 議事録を書いた時点で、管理の入力が完了している |

- 「ドキュメントを書く機能」と「データベース機能」が**同じ製品の中で繋がっている**こと
- これがS10の仕組み（議事録＝案件管理の入力）を成立させる唯一の条件

**話法メモ**: 「一元化したい」だけでは理由にならない（「OneNoteに一元化すればタダ」と返される）。**「文書ではなくデータになる」という一点に絞る**ことで、初めて他ツールとの差が説明できる。第2部の中核。

## S14. 他のツールとの比較

**メッセージ**: 用途が異なるため、既存のBacklogは継続して使います。

| | Backlog（システム開発部） | Notion（全社） |
|---|---|---|
| 対象 | 社内システムの改修課題 | 研修案件・議事録・社内ナレッジ |
| 使う人 | 開発メンバー | 全社員（営業・運営・講師管理・機材・コンテンツ・PMO） |
| 方針 | **現行のまま継続** | 新規導入 |

- システム開発部でBacklogが機能しているのは事実であり、**置き換える提案ではない**
- 開発課題の管理と、部門横断の案件管理＋議事録の統合は、求められる構造が異なる

**話法メモ**: 攻めではなく守り。**Backlogの階層構造（親子・孫課題）の話には踏み込まない**——技術的に細かすぎるうえ、「じゃあBacklogの機能追加を待てば？」という返しを招く。時間が押していれば、このスライドは飛ばして別添Bに回してよい。

**話法メモ**: 「全社即導入」は費用と審査の両面でハードルが高い。しかし**ライセンス（全社）と業務移行（段階的）を分けて説明する**ことで、「いきなり全部やるのか」という不安を消しつつ、全社ライセンスの必要性は譲らない形にできる。

# 別添C: 数字の作り方（試算シート）

## C-1. 時間単価の算出

```
時間単価 = 平均年収 × 1.25（法定福利費等） ÷ 年間労働時間
        = 450万円 × 1.25 ÷ 1,900時間
        ≈ 2,960円 → 3,000円/時 として計算
```

※ 年収レンジは350万〜900万と幅があるため、**平均値で計算していることを注記する**。役員層が多く参加する会議のコストはこれより高くなるが、控えめに見せるため平均値を使う。

## C-2. 会議コスト（課題B）

```
年間会議コスト = 100名 × 週◯時間 × 45週 × 3,000円
目的曖昧分     = 上記 × 35%（体感3〜4割の中央値）
削減見込み     = 目的曖昧分 × 30%（控えめに設定）
```

**⚠ 「週◯時間」は Viva Insights / Teams利用状況レポートで実測すること。**

## C-3. 手戻り・遅延コスト（課題A）

```
年間損失 = 1,000件 × 遅延・手戻り発生率◯% × 1件あたり追加工数◯時間 × 3,000円
```

**⚠ 発生率と追加工数は実測が必要。** 過去半年の案件から数件をサンプル調査するのが現実的。**数字を作れない場合は、金額換算せずS7の実例による定性説明にとどめる**（無理な数字は突かれる）。
